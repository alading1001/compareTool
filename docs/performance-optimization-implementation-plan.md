## 1. 任务目标与完成标准

### 1.1 要解决的问题

这个项目是 Windows 桌面代码比较与交付工具。它支持 Git、SVN、文件夹、压缩包、Git 多版本、SVN 多版本，以及混合多项目；生成单文件 HTML、上线操作说明和 oldVersion/newVersion 变更文件。

本轮要减少以下可重复观察到的成本：

1. 长行和位于修改区间中间的重复行，在完整差异匹配中产生的平方级工作。
2. 同一固定仓库端点被重复读取，同一固定属性由不同对象重复查询。
3. 压缩 TAR 被多次顺序解压，排除成员仍全部先写入临时目录。
4. Git 虽已批量读取 blob，但仍按文件路径启动许多微小检出探针。
5. 相同 glob 规则在每次匹配前重新转换为正则字符串。
6. 生成端保留不再需要的旧新正文和全部 HTML；浏览器又复制整份 HTML 数据。
7. 路径和事务检查中，同一阶段重复查询元数据；历史可选限制分支增加维护复杂度。

目标是**减少相同结果所需的工作**。完整性、端点含义、导出字节和失败恢复行为属于验收条件，不能拿来换取速度。

### 1.2 完成后应交付什么

- 实际修改的源码及有意义的新增/调整回归测试。
- 可重复的性能基准入口，而不只是一次终端截图。
- 优化前后的原始数据、运行环境、统计口径和正确性核对结果。
- 一份逐项说明“已完成 / 保留原实现并说明原因 / 待目标环境验证”的验证报告。
- 与最终代码一致的项目技术文档；用户操作变化时同步维护说明书。
- 单独列出 Windows、真实浏览器、内网 SVN 或其他无法在实现环境中完成的验证。

不要求为了证明做过优化而修改每个模块。若某项方案无法证明兼容性，保留原实现并交付具体分析，继续完成其余独立事项。不得把这样的项目写成“优化完成”。

### 1.3 本轮不做的事项

- 不重新打包正式 EXE，不修改 `app_version.py` 的版本号，不改动现有构建身份和正式 `dist/CompareTool.exe`。
- 不提交、不推送、不发布；这些需要后续单独的明确指令。
- 不修改用户的 `compareTool_config.json`、真实输入目录、业务仓库或历史输出。
- 不重写多版本文件身份规划，不改成共同基线、cherry-pick 或 merge。
- 不改变默认全文展示、不修改默认排除规则的内容、不默认开启包内递归。
- 不引入按文件数、文本长度、预计耗时拒绝正常任务的限制。
- 不借本次工作扩展对 Git filter、LFS、SVN keywords 等转换能力的支持。
- 不进行全仓库风格重构，不为统一抽象而新建通用框架。

这些是本任务范围，不代表今后不能单独提出相应功能。

## 7. 批次 A：先消除低成本、可定位的重复工作

### A1. glob 编译结果复用

**修改入口**：`vcs/base.py` 的 `set_exclude_patterns`、`_is_excluded`、`_is_excluded_tree`、`_match_glob_pattern`。

**现状**：每条路径对每条规则都重复执行斜杠规范化、隐式 `**/`、占位转换、`re.escape`、字符串拼接。Python 的正则缓存不会消除这些前置转换。

**推荐设计**：优先采用纯函数“规则字符串 + implicit_any_depth → 编译后正则”的有界缓存。缓存只负责规则转换，`_match_glob_pattern` 对路径继续执行匹配。保留现有静态方法调用形式。

之所以优先选纯函数缓存，而不是仅在 setter 中编译，是因为实际测试与部分内部桩直接执行 `vcs.exclude_patterns = [...]`，有的使用 `__new__` 绕过初始化。只依赖 setter 容易出现规则已变但编译缓存未变的错误。

缓存可设有限条目数控制自身内存，例如几百或上千条；这是缓存淘汰策略，不是用户输入上限。未命中重新编译，不能拒绝新规则。不要缓存全部被检查路径，也不要为缓存给匹配结果设规模限制。

必须保持：

- 普通路径与目录剪枝的 `implicit_any_depth` 分开作为缓存键。
- 当前 glob 语法原样保留，不趁机增加 `?`、字符类等与现有正则转义不同的行为。
- `/` 与 `\`、无斜杠模式、末尾 `**`、`**/`、大小写语义不变。
- 目录剪枝仍由同一条规则证明直接及嵌套后代都被覆盖，不能拼接两条规则作证明。
- rename 两侧分别过滤；跨边界继续变成 A 或 D。

**验收**：默认规则样本结果完全相同；增加动态换规则、直接赋值、普通/剪枝模式相同字符串、Windows 路径、`foo/*` 与 `foo/*/*` 等边界回归。以结构计数证明规则转换次数接近不同规则/模式组合数，而非路径数 × 规则数。三次基准报告中位数，不把时间阈值写成容易抖动的单元测试。

### A2. 无 EOL 转换需求时不扫描 NUL

**修改入口**：`vcs/svn_vcs.py::export_file_to_path`、`_get_eol_style` 及固定属性缓存；辅助扫描位于 `vcs/base.py::_file_contains_null`。

当前顺序是 raw 导出 → 全文件 NUL 扫描 → 读取 EOL 样式 → 可能改写。当固定属性已经说明不进行 EOL 转换，NUL 结果没有用途。

**推荐顺序**：在不引入额外仓库查询的前提下取得已固定的有效 EOL 决策；raw 正常导出成功后，无转换直接返回；需要转换时保留原有 NUL 判定与转换规则。

这里有一个兼容细节：独立调用 writer 的旧调用方可能尚无属性缓存，当前二进制含 NUL 会在属性查询之前返回。不能机械把 `_get_eol_style` 提到最前面，导致这种原本可用的调用新增属性读取失败。可以先为已知缓存状态提供快路径，未知状态走原逻辑；若统一重构接口，须为直接调用补足兼容验证。

不要仅按文件扩展名判断二进制，也不要把 `native` 固定为某一种平台换行。属性为 LF/CR/CRLF 时，保留当前规范化方式；有 NUL 的文件不能因优化而开始被错误转码。

**验收矩阵**：无属性、空值、native、LF、CR、CRLF；空文件、普通文本、含 NUL 文件；已有 CRLF、混合 CR/LF、跨分块边界；直接调用 writer 与 GUI 正常路径；raw 导出失败、属性读取失败和转换失败。指定的无 EOL 6 文件样本 NUL 扫描应从 12 次变为 0，导出逐字节相同。

### A3. SVN 多版本与内容读取对象共享固定属性

**修改入口**：`SVNMultiVersionVCS._get_svn_properties`、`_validate_svn_regular_endpoint`、`_content_vcs` 的配置；`SVNVCS._get_properties`、`_get_eol_style`。

优先保持一处权威属性读取。可将多版本已解析的属性以明确方法交给内部 SVNVCS，或让两者使用同一个任务内 provider；不要简单通过复制两个私有字典假设键的含义一致。

缓存身份至少要能证明对应同一固定仓库身份、历史 URL 和数字 revision。若对象本身已固定 UUID/仓库 URL/peg，则局部键可较短，但必须记录这一前提。尤其不能只使用显示版本字符串与报告相对路径作为跨对象共享键。

必须处理：

1. `rNNN` 与 `NNN` 规范化，但报告显示标签保持原样。
2. 项目根或祖先移动后，相同项目相对路径对应不同历史 URL。
3. 两个仓库、两个子项目、相同文件名与相同 revision 不能串用。
4. 任务中工作副本被 switch，不能重新按当前工作副本定义缓存身份。
5. 含编码标记的属性值仍保留原语义；keywords、externals、special、executable 不能因共享而漏判。
6. 不可把网络失败缓存为空属性；只缓存成功、完整解析的结果。
7. 共享字典的调用方不得原地删改属性。可复制轻量字典或使用受控只读视图，不要求构建复杂通用缓存框架。

**验收**：指定 6 文件 SVN 多版本样本，12 个实际端点最多各执行一次成功 proplist，目标由 24 降至 12；普通模式不能倒退。复杂目录属性查询按其真实端点单独计数，不为凑目标而跳过目录属性。

## 8. B1：差异匹配算法优化

### 8.1 行内公共字符边界

**入口**：`stable_diff.py::_changed_pair`。

推荐步骤：

1. 对已经进入该函数的字符序列求最长相同前缀。
2. 在不越过前缀的范围内求最长相同后缀。
3. 对中间真正变化区间运行现有字符匹配。
4. 按原顺序输出前缀、变化部分、后缀；使用原转义/空格/tab 处理函数。
5. 中间任一侧为空时直接生成纯增加/删除部分，避免无意义匹配。

必须在完成字符身份比较后做 HTML 转义。不能先把未知字节/特殊分隔符变成可见标记再比较，否则真实字符可能与原文中的字面标记合并。不得吞掉末尾字符，也不能把 tab 与等宽空格合并。

允许在重复字符导致多种等价对齐时改变标色的边界，但必须：保留双方所有字符、对真正不同字符有明确提示、遵守原说明卡与表格语义。小修改的既有显示应尽量稳定；若视觉对齐有变化，给出前后样本而不是只说测试通过。

### 8.2 中间大量重复行

**入口**：`stable_diff.py::_line_groups`、必要时 `prefer_stable_diff`。统计入口 `DiffEngine._count_line_changes/_lcs_length` 保持独立，不把近似显示对齐用作精确行数统计。

先复现 E02，再选择实现。建议按复杂度从小到大考虑：

1. 对边界变化但中间同序重复块的案例，识别可证实的等值块，分段处理其余区间。
2. 使用单调且不会跨越的等值锚点；候选必须核对原始完整行相等，哈希只用于索引。
3. 若唯一锚点不足，考虑重复游程或其他保证有进展的分块策略，不能继续展开重复元素的全部配对。
4. 无法确定某个优化分块合法时，保留原有完整匹配或选择经过高亮质量验收的完整回退；不能漏行、截断明细或报“文件太大”。不能把整段机械按行号配对作为无条件快速回退。

不要把 `autojunk=True` 当成无需证明的修复。它可能改善性能，也可能吞掉重复行的有用对齐；若使用，应只属于经过验证的显示策略，并验证上下文不会隐藏真实变化。也不要直接提高递归深度。

建立一份内部 opcode 合同：旧新区间单调、无重叠、不倒退；全文模式覆盖两侧整个输入；equal 区间长度相等且逐行真实相等；add/delete/replace 合法；上下文裁剪只发生在得到可信编辑结构之后。

**高亮质量也是正确性的一部分。** 对能够稳定识别的长公共块，应保留其对齐和相同标记。只在重复块前插入或删除一行时，不能因为位置偏移把后面的长公共块大面积标成替换。左右正文完整还原、精确 LCS 统计正确，都不能单独证明展示合格。

不要求重复内容只有一种对齐，也不要求新旧 HTML 或红绿边界逐字相同。选定具有明确长公共块的代表性样本，记录锚点、相同行/变化行的展示范围并保留前后报告或截图；人工核查插入、删除、重复块移位的可读性。任意输入的最佳对齐不作为本轮承诺，但不得以大面积额外标色换取指定样本的速度。

### 8.3 验证样本

- 相同前缀、相同后缀、两端均修改而中间重复。
- 单条超长行、少量长行（不足 64 行）、64 行及以上批量替换中夹长行、多个不同长行。
- 重复块前后插入/删除、相邻交换、重复值很多但位置不同。
- 完全相同、空→非空、非空→空、两端不同长度、纯新增/删除。
- 中文、多字节编码、surrogateescape、真实 U+2028 与字面 `⟦U+2028⟧`、NUL 二进制路径。
- CRLF/LF/CR、最后一行缺换行、tab 与空格。
- 全文/上下文、普通文本/包内文本、单项目/多项目。
- 小规模随机案例与独立 oracle；解析左右 HTML 还原输入，不比较随机 DOM id。

每个长行样本还必须通过真实 `DiffEngine` 调用链，记录实际采用标准 HtmlDiff、主动 stable 渲染还是递归失败后的 stable 回退，以及选择原因。当前 `prefer_stable_diff()` 对不足 64 行的输入通常不会主动选择 stable；只证明 `_changed_pair()` 变快，不代表单条或少量长行的实际引擎路径已经改善。若调整切换策略，64 仍只是算法选择条件，不能成为输入上限；原小修改的高亮质量也须验收。

### 8.4 性能验收

至少测 2k/4k/8k 三档及三次重复。目标是在 E01/E02 这类可消去的重复工作上明显改变增长趋势，而不是仅小常数改进。新实现若仍接近“输入翻倍、耗时四倍”，不能把该热点写成解决。

不要求对所有任意输入承诺线性复杂度，不把某个秒数设成跨机器强制门槛。必须同时证明输出完整、统计正确、已知长公共块对齐合理；性能结果单独于 tracemalloc、完整回归运行，避免测量互相干扰。结果按实际渲染路径分别列出，未改善的路径如实标记，不能由辅助函数成绩外推。

## 9. B2：固定端点只获取一次原始内容

### 9.1 先区分四种数据

| 数据 | 用途 | 可以怎样复用 |
| --- | --- | --- |
| 仓库原始字节 raw | 编码/格式识别、原始净变化、原始签名 | 同一固定端点在任务内复用 |
| 检出规则处理后的交付字节 export | oldVersion/newVersion 与递归分析 | 从固定 raw 加固定转换策略派生 |
| 已完成导出的 stage | 报告包内递归、最终事务提交 | 只能由 exporter 返回的实际路径借用 |
| 展示正文/HTML | 给人审查 | 不能作为真实字节导出来源 |

raw 与 export 在很多文件上碰巧相同，但不能由此合并两种合同。尤其是 Git autocrlf、显式 text/eol、SVN eol-style 和格式变化，必须保持两套概念。

### 9.2 多版本优先采用成对端点写入

当前 `_MultiVersionFolderDelegate._finish_plan` 分别调用 content_writer 和 raw_content_writer，导致同端点内容被取两次。

推荐增加一个任务内“写入一对端点”的内部能力，示意流程如下；具体接口命名可按代码最小改动确定：

```text
确认固定版本、路径、普通文件类型和端点属性
    ↓
为 raw 与 export 分别占有合法目标路径
    ↓
从固定仓库端点流式获取 raw，完整成功后才标记可用
    ↓
从 raw 流式生成 export；使用原 Git/SVN 转换逻辑
    ↓
两份端点都成功后进入原净零判断和规划结果
```

要求：

- 文件类型、svn:special、keywords 等最终端点校验仍在净零过滤之前执行。
- 旧/新版本仍按每个 logical file 的端点决定，不使用整个项目的统一 new。
- 同一路径在不同 revision/commit 是不同端点；rename 的旧路径不能被新路径覆盖。
- 单端点写入失败，不把已完成的另一个端点当成本次成功。
- raw 与 export 若需要两个文件，使用独立普通文件。不要用可能共享修改的硬链接优化复制。
- 可采用“复制并转换”单遍处理，但不得先转换 raw 本身再把它当原始内容返回。
- 大文件始终分块；不能同时在内存保留旧raw、新raw、旧export、新export四份完整 bytes。
- 对旧内部 writer 接口保留兼容层或同步改全调用，不引入两套永久重复实现。

先抽出并复用已有转换逻辑，再改变获取顺序；不要在本项另写一套行为略有不同的换行算法。

### 9.3 普通 SVN 的任务内磁盘缓存

普通 SVN 正文与最终导出也会各 cat 一次。可为确实会被多次消费的固定端点建立任务内 raw 磁盘缓存：首次正文读取时流式获取到私有文件，后续签名/导出复用。

缓存只在一个固定任务生命周期内有效，不在应用全局或不同项目之间共享。端点键必须由固定仓库身份、历史 URL 和数字 revision 确定；不使用用户的 HEAD 标签、工作副本路径或报告显示标签。

成功缓存至少满足：进程成功退出、输出完整、文件句柄关闭、没有写入异常。用“私有写入中目标 → 成功可用条目”的状态区分，失败不能留下可命中的半文件。不能把 None/读取失败缓存成空文件。

**完成态与后续内容一致性分别保证。** 新增磁盘缓存不能只以“路径存在且首次写入成功”作为永久可信依据。条目至少绑定逻辑端点、完成态、字节长度和在成功写入过程中计算的内容摘要，并按现有安全读取能力保留/核对文件身份。内容摘要只记录首次成功发布的值，不能消费时重新定义基线。

- 后续正文、签名和交付消费者必须读取同一份已发布内容。继续使用拒绝链接/联接点及检查文件身份的安全路径，读取前后检查句柄身份；需要时核对路径与句柄身份。仅比较大小/mtime 不能发现同大小同时间戳改写。
- 本版采用在已有的完整读取、复制或转换输入流中累计摘要和字节数，核对与发布值相同；不得为每个调用额外加一轮“先扫描再读取”。不新增跨所有消费者长期持有缓存句柄的资源管理方案。
- 校验结束前，该消费者的结果只能处于未提交状态；不匹配必须中止本次生成，保留原输出。报告生成所见与随后导出所见不能分别接受两份内容。
- 部分读取不能声称验证了整文件摘要；若存在只读前缀的消费者，标清该结果的用途及后续完整读取的校验时点，校验通过前不提交派生产物。没有后续完整读取且该部分结果影响最终产物时，先核对这条特殊调用链再选择最小补充，不默认让所有调用多读一遍。
- 缓存受损时不得悄悄重新下载、更新摘要后继续混用先前结果；本轮采取明确失败。现有 stage 的绑定、锁内复核和恢复验证仍然保留，raw 缓存身份不能替代它们。

以上是新增缓存必须满足的设计约束，不是已复现的当前产品漏洞。

不必为仅导出一次的二进制文件强制增加一份 raw 磁盘副本。可以保留直接流式导出路径；若某端点后来确实被重复使用，再按明确策略复用。不能为获得缓存收益给所有文件先做网络大小查询或全量预下载。

如果普通 SVN 开始拥有新缓存目录，就必须有明确 cleanup，并把 `main.py` 中普通 SVN 当前不需要 cleanup 的分支一并调整。成功、失败、零变化、多项目后一个失败、模板失败时都要释放；有效恢复日志保护的 stage 仍按原规则保留。

### 9.4 Git 的范围

Git 原始读取已经使用 `cat-file --batch`。本项主要修复多版本同端点重复读取；不要仅为了形式一致，给普通 Git 强行增加新的全内容磁盘缓存。

Git 源对象本身固定，但转换属性/配置必须来自任务快照。将 `export_file_to_path` 中“获取 raw”与“从 raw 生成检出字节”的逻辑分离时，仍保持属性验证、自动文本判定和不执行外部转换程序。

### 9.5 功能与失败验收

- 指定 SVN 多版本样本应从 24 cat 降至 12，最终属性查询保持 A3 的 12 次；若存在明确附加读取，逐一解释，不隐藏计数。
- 普通 SVN 正文+导出样本也应接近每个实际端点一次内容获取。
- Git 记录逻辑 blob 请求数、传输字节数和进程数三个指标；batch 进程仍是一个不代表重复读已消除。
- 原始字节与检出字节不同的真实矩阵必须覆盖；不能只测 LF 且无属性。
- 选中版本之后移动 tag、SVN switch/HEAD 变化，缓存不能混入当前状态。
- 首次内容获取失败、读中异常、磁盘写满/拒写、raw 成功而转换失败、导出复制失败，都保持整次失败和旧产物完整。
- 成功发布缓存后、两个消费者之间，注入同大小同 mtime 改写、替换和删除；必须由实际生效的持有保护阻止修改，或由消费校验发现并在提交前失败。另测消费中短读/改写，不能只测半文件未发布。
- 原失败注入若恰好放在被优化掉的“第二次下载”上，需要移到真实的新边界验证。不能保留不存在的网络依赖，也不能简单删掉整个失败恢复场景。
- 缓存后内容已固定，后续服务不可用不应要求再下载一次来故意制造失败；这属于稳定端点复用的正常结果，应写明。

## 10. B3：TAR 预检后顺序提取，消除重复回读

### 10.1 先只优化读取顺序

**入口**：`vcs/archive_vcs.py::_preflight_archive_size`、`_preflight_tar`、`_extract_tar`。

当前压缩 TAR 的工作大致为：

```text
完整预检解压 → getmembers 完整扫描 → 回头按成员抽取
```

第一步应保留，目标是：

```text
完整预检解压 → 第二遍按顺序验证并抽取
```

不要一开始把预检、空间选择、提取和预算全部合并。先消除一个确定的重复读取阶段，保持失败发生前的检查含义。

### 10.2 实现要求

当前 `_preflight_tar()` 内部检查过成员并最终返回总展开字节，不能假定它已经向调用者提供完整的复用计划。改造时优先返回或内部保存一份轻量、不可变的预检结果，供 B3 第二遍提取和 B4 过滤共用：

- 按归档顺序记录第二遍核对所需的最终有效成员名、种类、声明大小及必要权限信息，附总成员数、总展开量和完整顶层/目录结构信息；采用最小描述，不额外保留正文或完整 PAX/GNU 载荷。
- 有效名称/大小必须按 PAX/GNU 覆盖后的含义记录；第二遍逐项核对顺序与这些字段，并检查少成员、多成员、短读和末尾错误。不要只核对总数与总字节。
- 复用已有预检中建立的数据，避免再保存一份完整 `TarInfo` 列表或为单根、预算、过滤分别重新遍历压缩流。不为省内存新增默认路径长度或元数据性能上限。
- 单根选择依据完整结构；B4 的路径映射和不可变过滤计划由该结果派生，不能反过来缩小安全预检范围。旧内部调用及测试夹具须同步检查，不遗留一套相互不一致的 size-only 校验路径。
- 当前 `_ReportArchiveVCS._validate_archive_limits()` 承接声明预算预留，而 `_CountedWriter.write()` 承接实际字节累计。替换 `getmembers()` 时必须显式保留这两类合同的实际入口；同一归档只预留一次，第二遍不得重复预留，也不能因改用新预检结果而绕过子类的共享预算。

- 实际使用的 Python tarfile 流式接口必须验证后再采用；可考虑 `r|` 家族或其他明确不会回头解压的顺序处理方式，不凭 API 名称猜测行为。
- TAR 原始流已由 ArchiveVCS 同时持有两侧稳定源句柄。沿用借用流包装，不能重开源路径来解析另一遍。
- PAX/GNU longname/longlink/global metadata 的最终有效名称、大小、type 必须与预检含义一致。
- 预检和提取必须同样拒绝路径穿越、绝对/盘符路径、ADS、符号链接、硬链接和设备节点。
- 不使用无过滤的 extractall。
- 目录项与文件项冲突、重复成员、实际 Windows 别名碰撞按现有规则处理。
- 每个成员按流式块写入；写入错误立即失败。结束前确保成员内容没有短读、压缩流没有未处理错误。
- 不能只因为预检通过就省掉真实落盘时的路径/排他创建检查；目录可能在两个时点之间被替换。
- B3 全量提取仍按完整展开需求选择临时根；启用 B4 时按第 11.2 节区分全部展开安全预算与实际需保存的内容。不提前构造一份完整未压缩 TAR 作为替代缓存。
- POSIX 与 Windows 的源稳定性处理保持原有差别；不能照搬 Windows deny_writes 的结论删除 POSIX 摘要复核。
- 8 层、100,000 成员、10 GiB 的递归共享预算必须继续累计，不能把第二遍处理重复计为两个不同包，也不能漏掉实际写入。

Python 3.12 官方说明确认 `r|` 家族按块处理且不随机寻址；这是候选接口的能力依据，不能代替本项目源句柄、预检和错误行为验证。[Python tarfile 文档](https://docs.python.org/3.12/library/tarfile.html)

### 10.3 验收

覆盖 tar、tar.gz/tgz、tar.bz2/tbz2；空包、目录记录、Unicode/长名、PAX/GNU 元数据、可执行权限、损坏/截断包、重复或冲突项和真实安全拒绝案例。

同一合成样本按解压后的读出字节计数，应从约三遍降到约两遍；允许 TAR 记录/填充带来小额差异，不写死 gzip 私有实现某次 read 次数。解压结果每个文件的字节和元数据与基线一致，主比较/导出也要验证。

压缩流读取量、磁盘写入量、峰值内存和墙钟时间分开报告。改成流模式但为了验证又额外完整扫描，不能声称已经减少遍数。

## 11. B4：让排除规则在归档写盘前生效

### 11.1 为什么这项不能只是加一个 if

当前 ArchiveVCS 构造函数完成解压后才收到 `set_exclude_patterns`。提前过滤会影响的内容不止最终文件清单，还包括：单根目录判断、损坏成员错误、目录删除说明、全归档安全预算、元数据映射和后续切换排除规则。

因此必须先定义以下保持不变的行为，再改提取循环。

### 11.2 本轮采用的保守语义

1. **安全和资源预检覆盖整个原始归档。** 排除的危险路径/特殊节点/数量或展开预算超限不能被隐藏。
2. **优化路径中，被排除成员的正文写盘字节为 0，仍保持原有损坏检查。** 第一阶段统一保留目录骨架与零字节名称占位，不追求减少文件创建次数。公共兼容路径仍全量提取，分别计量，不能把“正文不写盘”等同于“不发生任何文件系统创建”。ZIP 需要读取到能触发既有 CRC/加密/压缩数据错误的边界；必要时将解压内容消费到丢弃 sink，而非直接不读。
3. TAR 中跳过的内容也必须正确消费到下一成员，截断不能变成正常 EOF。不要凭 skip 字节数绕过原来的错误语义。
4. 实际解压字节的计量应覆盖被丢弃的内容，不能通过排除规则绕过递归工作预算。当前递归预算的实际消费发生在 `_CountedWriter.write()`；增加丢弃路径时必须把等价计量放到它也会经过的内容消费入口。不能漏算排除内容，也不能在读取和写入两边把同一实际展开字节算两次。预检声明预留与第二遍实际消费保持原有两套含义，不再为预检额外累计一份实际提取量。
5. 允许减少落盘，但不承诺这项同时大幅减少 CPU 解压。若想进一步跳过被排除 ZIP 的内容校验，那是另一项兼容决策，本轮不默认做。

**名称校验的边界：** 现有 `_open_archive_member_target()` 和目录创建逻辑的一部分安全性，依赖在目标文件系统真实创建名称及检查目录项。Windows 长名称可能产生 8.3 别名，且该功能受系统/卷配置影响；不能用归档名称字符串精确推断，也不能把所有带 `~` 的名称判错。[Microsoft 文件命名说明](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)

本版选定的最小策略如下：

- 在实际解压目录按原有成员顺序继续创建全部合法目录和普通文件，复用 `_ensure_archive_directory()`、`_open_archive_member_target()`。保留成员正常写正文；排除成员保留零字节文件并把源内容读入丢弃 sink。ZIP 保留先 `zf.open()` 成功再创建目标的顺序，防止改变已有句柄释放边界。
- 占位保留到专用临时树整体 cleanup，不逐成员删除，不增加单独的清理协议。它们位于任务内部树中；过滤后的文件清单、权限变化清单、递归正文和最终交付不得包含占位。目录结构及权限元数据可以继续沿用原流程，重点验证最后输出等价，不为此重写公共 FolderVCS 过滤顺序。
- 不增加“名字看起来安全就免创建”的分支，不模拟 8.3 分配，不在另一卷/目录试建后推断真实位置安全。合法字面 `ABC~1.TXT` 与实际别名冲突仍由现有真实路径检查区分。这保留了文件创建成本，但消除了优化路径中的排除正文写入；耗时收益取决于实际内容规模，不能由写盘次数直接推断。
- 新优化只进入显式不可变排除计划的内部路径；原公共构造及需要动态 setter 的调用保持全量提取，验收单列为兼容路径，不冒充优化命中。若某个明确场景仍无法通过等价验证，暂不启用该场景优化并记录原因，不用多层自动回退掩盖缺口。

**空间与预算的两个口径：** 全归档成员数、声明/实际展开字节、压缩比和递归共享预算继续覆盖全部成员。临时磁盘空间选择则依据真正保留的成员正文、名称占位/目录开销及合理余量；这些估算不等于精确文件系统分配量。B3 单独实施或未启用优化的兼容路径仍按全量提取需求计算；模式在选择临时根前确定，不做落盘到一半才切换全量提取的隐式回退。不得为得到更精确估算再完整解压一遍，或引入正常输入的固定空间性能上限。

“保留错误语义”指危险路径、名称冲突、损坏数据、预算和实际 I/O 失败仍正确处理，不要求复刻已被优化消除的操作错误。例如减少正文写入后，原先因全量解压空间不足的样本可以成功，这是本项预期收益；不得为了保持旧失败结果强行要求全量空间。多个错误同时存在时也不强求报错先后顺序逐字相同。

### 11.3 正确处理“忽略最外层单一文件夹”

先用完整成员结构判定是否恰好一个真实顶层目录且无其他顶层项；不能先过滤掉顶层文件后“制造”单根。

old/new 两端独立确定只剥离一层的前缀。再把完整成员名映射成比较相对路径，并按该路径执行用户规则。完整结构要包含隐式目录、显式目录项和空目录，沿用现有接受/拒绝行为。

例子：

```text
old: release-old/classes/A.class, release-old/conf/a.txt
new: release-new/classes/A.class, release-new/conf/a.txt
选项：忽略一层；规则：classes/**
```

规则应作用在 `classes/...` 上；不能用 `release-old/classes/...` 匹配。两端前缀不同不妨碍各自正确归一化。新增/删除/rename、权限元数据、目录删除说明和 comparison_note 必须使用同一映射。

### 11.4 推荐接口与生命周期

可给构造函数增加可选的初始排除计划，并由单项目、多项目、递归 Inspector 在解压前传入。但现有“先构造再 setter”的直接调用必须仍可用，且不能造成后续放宽规则找不到已丢弃文件。

推荐把稀疏提取限定在明确的内部不可变计划模式：GUI/递归流程知道本任务规则不会再变，可以显式选择；默认公共构造仍保留完整提取和 setter 行为。或者采用惰性首次提取设计，但须证明不会意外延长源句柄持有、改变错误时机或读取被替换的归档。

不要让所有调用默认稀疏提取，然后 `set_exclude_patterns([])` 时静默漏文件。若设计选择限制任务内变更规则，应将限制只放在新的内部能力上，并保持旧公共路径可用。

提取出来的目录骨架如何保留应有明确规则，尤其空目录被新文件替代时仍需正确生成目录删除说明。仅以实际写出的文件反推完整目录结构可能漏掉该语义。

### 11.5 递归范围与验收

包内规则继续按每层现有相对路径含义执行，不把宿主 `server.tar/...` 前缀混进成员过滤。预算在整份报告共享，多项目不能重置。

必测：默认关闭优化时原行为；无排除；只排 `.class`；目录规则；单层通配不误剪嵌套；同一条规则证明剪枝；不同顶层名字；非法单根；空目录替换；rename 单侧排除；被排除但 CRC 损坏、加密、穿越或特殊节点；排除导致展示零变化；六种来源的递归开关一致性。

E08 普通样本目标是被排除成员正文写盘字节为 0；文件/目录占位创建次数另列。所有原来应该失败的安全/损坏场景仍失败，报告主清单及 old/new 交付不变。增加真实 Windows 8.3 别名启用/不可用环境下的名称组合核验：有实际冲突仍拒绝，合法 `~` 字面名仍接受；环境无法制造实际别名冲突时标记未验证，不以字符串测试代替。

同时构造“全部展开量大于可用空间，但实际保留量加余量足够”的空间选择测试，以及全量兼容路径空间不足的失败测试。安全预算仍按全部成员生效。故障注入可验证空间决策，但应与真实磁盘验证区分，不需填满用户磁盘。

## 12. B5：Git 原生检出探针与 mode 查询批量化

### 12.1 保留原生判断的原因

`git_checkout.py::conversion_mode` 使用两个微小 blob 让隔离 Git 确认 none/auto/text。它解决的不只是 eol 字符串判断，还包括配置优先级、平台 native 以及 `filter=set/unset/unspecified` 字面驱动与属性状态歧义。

不能用 `attrs == attrs`、文件扩展名或“没看到 filter 命令”直接共享模式。`check-attr` 文本表面相同，不一定能证明原生解析状态等价。

### 12.2 首选评估：按固定端点复用原生探针进程

先在实际 Git 版本上做很小的能力验证：批量接口是否支持所需 filters/path 表达、长度与终止协议如何返回、`GIT_ATTR_SOURCE` 如何固定、错误如何影响后续请求。

二次审阅时本机 `git --version` 为 `2.53.0.windows.2`。官方文档列出了 batch 与 `--filters` 的组合及路径输入要求，支持将其列为候选路线；本次未执行转换协议探针，不能据此宣称已经验证可复用现有读取器。[Git cat-file 官方文档](https://git-scm.com/docs/git-cat-file)

不要直接把现有 raw `GitBatchReader` 的响应解析器拿来处理转换结果。转换后内容长度与原始 blob 头长度可能不同；只有明确验证协议才能写解析器。也不能把本来只处理微小探针的 filters 扩展到真实大文件。

若原生协议可可靠使用：

- 每个固定端点/隔离配置建立有明确生命周期的通道，串行发请求并完整消费响应。
- 一次普通 text 探针可判定 none；需要时才运行含 NUL/CR 的第二探针。
- 特殊换行路径若无法在协议中无歧义表示，回到现有单次方式。
- 缺对象、非 blob、短响应、超长/非法头、异常 stderr、写入失败、进程退出须关闭或使通道失效；不能沿用可能已错位的流。
- 保留用户显式超时策略；关闭任务时终止/等待子进程并释放 stderr 文件。

如果协议不适用，记录实际命令与结果，改评估其他等价分组方案；不要凭空发明一个 Git 参数组合。

### 12.3 备选：按可证明等价的策略共享结果

只有在能消除属性状态与字面值歧义、固定 endpoint 与全部有效配置、证明路径不会再影响结果时，才允许共享探针结果。缓存键应包含证明所依赖的状态。

若为了构造这个键需要自己重写整套 Git 属性解析，通常不值得；保留逐路径探针比实现不完整的复制品更好。可以单独完成 mode 批量化而对 conversion_mode 保持原实现。

### 12.4 Git 多版本 mode 查询

当前 `_validate_git_endpoint_mode` 首次按 `(version, path)` 调用 `ls-tree`。可按实际固定 commit 分组，一次读取所需路径集合并校验返回完整性。

避免每个端点都列整棵仓库树；命令行超长时使用经验证的分组/协议，不能将 chunk 大小变成输入文件上限。路径当作字面路径处理，不能让 pathspec 通配符把兄弟项目纳入。

裸仓库、子目录作用域、跨边界 rename、大小写、Unicode、空格与换行路径均按现有合同映射。最终非普通 mode 仍在净零过滤前拒绝。

### 12.5 验收矩阵

- autocrlf false/true/input，eol native/lf/crlf；属性 text、-text、text=auto、eol。
- 层级 .gitattributes、系统/全局/info 属性快照与任务期间变化。
- 无程序 filter、clean-only、required、smudge/process；驱动名大小写与 set/unset/unspecified 字面名称。
- 已有 CR/CRLF、无 LF、含 NUL、非文本控制字符密度、末尾 Ctrl-Z。
- UTF-8/未知编码内容、大二进制与空文件；不把实际大内容送入 filters 探针。
- tag 移动、子项目、裸仓库、普通/多版本、显式超时与异常进程。
- native Git 对照：对受支持的安全配置建立隔离真实检出结果，比较实际字节；绝不执行用户仓库中的外部转换程序来做这个对照。

E05 的 24 次逐路径进程是当前基线，不要求通过缓存把不等价的端点凑到某个固定数量。成功优化必须报告探针逻辑次数、探针进程数、固定开销和完整字节验证。

## 13. 批次 C：报告生成与浏览器内存

### C1. 生成端 HTML 片段生命周期

**入口**：`diff_engine.py`、`stable_diff.py`、`report_generator.py`、单/多项目模板、`archive_report.py`、`main.py`。

先分两步实施，避免把“写到磁盘”误称为“从头到尾流式”：

#### C1a. 每文件生成完后落盘并释放

仍允许单个文件的既有 renderer 返回完整 HTML；应用内部立刻把已完成片段写到本任务私有存储，结果对象只保留轻量引用。后续模板逐块读取该片段。

**优先评估一个任务一个或少量追加式片段文件。** 引用记录所属存储、字节偏移和字节长度，避免一千个小片段默认对应一千个临时文件及大量打开/清理操作。首版不默认加分层内存缓存或 LRU；只有小报告实际测出明显退化时，再考虑简单有界缓冲并单独验证转存边界。缓冲预算只决定存储介质，不限制文件数、不截断报告。追加文件是优先候选，不是必须新建共享存储框架的硬性要求；若更简单方案经计量已满足内存和 I/O 目标，记录取舍即可。

采用追加文件时，完整写入并具备可读取条件后才发布引用；引用不能包含半片段。偏移按实际编码字节计算，读取严格限定范围并正确处理 UTF-8 字符边界。重复读取引用不依赖共享文件指针的残留位置；若引入并发读写，必须处理定位、缓冲刷新和发布顺序，不能为本项无故增加并发架构。失败条目不得被模板消费，失败处理仍使用任务资源生命周期。

这一步目标是把“所有文件 HTML 的累计驻留”降低到“当前正在生成的文件及写出缓冲”。它不能解决单个超大文件本身的峰值，报告中必须明确。

推荐的最小接口具有以下能力即可，不要求固定类名：

```text
HtmlDetailStore（由任务拥有）
  add_fragment(text) -> 只在本任务有效的引用
  iter_fragment(ref) -> 顺序输出文本块
  close() -> 成功/失败后统一释放；不接管源码 stage

FileDiff
  默认公共路径：side_by_side_html 仍可为原有字符串
  内部节省模式：保存片段引用，模板明确选择迭代路径
```

不能实现一个在 `str()`、`__html__()` 或 property 里把整个片段重新读成字符串的假流式对象。Jinja 模板也不能调用宏返回整棵包内子树字符串。

默认直接调用的 `FileDiff.side_by_side_html` 兼容性必须明确；优先将新存储限定在主工作线程显式传入的内部模式，不强迫所有旧调用方理解关闭后的临时引用。

生命周期要求：

- store 从任务开始存活到报告写出完成；多项目不能在前一个项目结束时删除后续总报告还要使用的片段。
- 包内 VCS 可以提前 cleanup，但已生成的成员片段由报告任务持有，不能指向被删除的解压树。
- store 自己拥有的临时文件与 exporter 的 stage、原始端点缓存分开管理。
- 报告生成失败、最终提交失败、用户窗口结束任务等现有路径均要收尾；有效 journal 保护的交付 stage 不受 store cleanup 影响。
- 片段只存生成后的 HTML，不把本机临时路径写入最终 HTML；最终结果仍是可独立打开的单文件。
- 片段读取失败必须中止报告，不能输出缺少某个文件但显示成功的页面。
- 仍复用现有最终 HTML 原子写入与事务提交，不因片段已落盘而直接写正式报告。

#### C1b. 单文件渲染也逐块输出

确认 C1a 的收益和剩余瓶颈后，再考虑给 stable renderer 提供迭代行/片段的能力；保留默认 make_table 的兼容封装即可。标准 HtmlDiff 的路径是否替换，需要额外视觉与内容证据，不为统一接口强行改小修改对齐。

metadata、格式说明、未知字节与特殊分隔符标记必须在正确阶段生成。以 UTF-8 分块读写时处理字符边界，不引入替换字符。测试里既检查最大输出块，也检查最终完整文本，不能只看模板 enable_buffering。

#### C1 验收

- 100/500/1,000 个文件与单个大文件分别测量；不要仅用一个小报告推断累计收益。
- 所有文件/成员内容、行号、说明完整，单/多项目、递归开/关、全文/上下文均验证。
- 峰值分别计量：已有结果对象基线、生成阶段增量、模板写出增量。注明 tracemalloc 不包括的外部进程与浏览器。
- 已有 `test_rendering_performance_regressions.py` 的递归 include 最大块回归继续通过。
- 注入片段写入/读取错误、报告最终写入错误，四类旧输出保持完整。
- 模板重复遍历同一文件片段不会因流已耗尽而第二次为空。
- 记录片段数量、临时文件数量、打开/关闭次数、写读字节和小报告耗时；共享存储不能串读相邻片段。覆盖多字节字符边界、空片段和重复读取；若实际增加内存缓冲，再覆盖转存前后，证明没有把内存成本转成明显的文件系统退化。

### C2. 浏览器按选择读取明细，减少启动复制

当前模板先生成隐藏 HTML，页面启动时再对每个隐藏元素取 innerHTML，保存在 fileData；点击文件又重新解析成可见 DOM。

#### C2a. 优先去掉启动时的完整字符串副本

此项可以在批次 0 后独立安排，不必等待全部 B 类或 C1 完成。实施、基准与浏览器交互回归独立记录，避免让后续片段存储改造掩盖本项收益或回归。

让 fileData 保存明细源的 id/引用，而非每个文件的 html 字符串。用户选择文件时才读取/克隆对应内容。

保留单文件离线使用，不依赖网络、fetch 本机旁边文件、CDN、外部服务或浏览器放宽安全选项。清单数据仍完整、manifest 默认复用 fileData，不为了按需显示而截断下载清单。

隐藏元素改成 `<template>` 需要单独理解：template 内容仍会被解析为惰性片段，不等于“没有 DOM 内存”。可以减少活动 DOM/初始化工作，但不能虚报为完全不解析全部内容。

显示区每次只保留所需内容；返回上一个文件时从原模板正确恢复。避免重复绑定事件、保留过期 anchors 或创建无界访问缓存。

#### C2b. 文件树与目录类型统计

当前渲染树时会为目录递归计算类型，并一次性创建全部文件节点。可将目录类型在树构建后一次自底向上计算；目录第一次展开再创建其孩子。

过滤和变更清单必须基于完整数据，而不是已挂载 DOM，否则未展开目录会被漏掉。所有类型过滤组合、项目根显示、同名文件与目录排序、rename 展示路径保持原行为。

只清理先前 active 节点引用，可避免每次点击遍历全树去掉 active；但切换过滤后引用可能失效，要有明确更新。

#### C2 验收必须含真实浏览器

- 单项目和多项目：点击、展开/折叠、类型过滤、清单生成/复制/下载、路径展示。
- 普通文本前后差异导航；左右键滚动与鼠标定位后的焦点。
- TAR → WAR → JAR → 文本逐层展开，局部导航不控制其他成员。
- 键盘激活按钮保留按钮焦点，鼠标定位内容后焦点交给对应正文。
- 来回切换普通文件与包内正文，重复展开不重复注册处理器。
- 路径包含引号、尖括号、`</script>` 等内容仍是普通文本，不能执行脚本。
- 控制台错误、未处理 Promise、实际 focus/scroll 和 DOM 数量。
- 初始加载时间、首次点开大文件时间、切换时间与内存分别测量。

现有 Node DOM 替身测试有价值，但不能代替真实布局、焦点、键盘和浏览器内存验收。若环境不能打开本地页面，可使用许可范围内的本地静态服务；不可绕过工具安全限制。不能运行时明确保留此验证项。

## 14. 批次 D：防御复杂度精简的实际边界

### 14.1 判断标准

一个检查可以简化，不是因为“代码多”或“正常用户不会这么做”，而是因为能说明：

1. 它保证了什么性质。
2. 同一性质是否已被同一作用范围、同一时点的可信证据覆盖。
3. 两个检查之间是否发生了路径、句柄、文件内容、所有权或并发状态变化。
4. 删除后会出现的失败案例是否仍被其他机制覆盖。
5. 验证成本是否高于实际收益。

可精简的具体例子是 A2 的无效 NUL 扫描、A3 的重复固定属性读取、A5 的同阶段元数据查询。不能将这些结论推广成“路径检查、摘要和事务签名都过度”。

### D1. 历史限制与兼容分支

先列出所有 MAX_*、超时、预算和 fallback 的调用方，将其分为：

| 类别 | 当前处理原则 |
| --- | --- |
| 归档炸弹、恢复日志结构等实际安全界限 | 保留；不按性能分支清理 |
| 默认 None 的普通规模/耗时策略 | 默认继续关闭；不得悄悄恢复限制 |
| 仍被明确调用方或测试注入的策略 | 保留契约，可集中实现但不随意删除 |
| 已无生产入口且无外部兼容承诺的死代码 | 证明后可删除，列出调用搜索证据 |
| 旧接口兼容 | 先确认调用方；有简洁包装就不必做破坏性重构 |

本项主要收益是维护成本，不预计显著提高运行速度。不要以本轮为由引入复杂策略插件系统，把简单的 None 检查改成更难追踪的配置框架。

对于 unsupported Git 转换、SVN keywords 等拒绝，必须区分“当前能力不足”与“重复防御”。未实现可靠转换前保留明确失败，不能输出原始字节冒充检出文件。

### D2. 事务跨阶段摘要：先画清状态，再决定是否实施

**本方案的默认实施范围只包含 A5 的同阶段元数据复用。** 跨阶段内容扫描的删减没有足够证据支持直接修改；本轮应交付可行性分析与明确结论。只有后续明确纳入该项且完成证明，才改动恢复协议。

至少画清这条链：

```text
生成前基线 → 锁内恢复/复核 → 记录 stage/target 身份
→ 移动旧 target 到 backup → 安装 stage 到 target
→ 写入 commit 决策 → 移动 backup 到 quarantine → 删除隔离对象
```

对每个扫描说明：观察的是旧内容还是新内容、当前路径是否可信、对象是否刚被移动、谁可以并发修改、失败后哪个 journal/marker 授权恢复。

基线 E10 中旧内容 7 次、新内容 3 次不能理解成“删除 8 次即可”。同一路径前后可能是不同对象，路径字符串不构成内容身份。

以下简化不接受：

- 使用 `(path, size, mtime)` 作为跨阶段内容摘要缓存。
- 检查过目录根就不再检查后代链接/对象替换。
- 只在移动前验证，去掉对实际被移动对象的验证。
- 把已分析 stage 的当前内容重新算作新基线。
- 删除 HMAC、忽略签名异常、把旧无签名日志当自动删除授权。
- 把进程还活着的其他任务 stage 当成自己的垃圾。
- 失败后清掉恢复需要的 journal、decision 或 stage marker。

如果提议用长期句柄/目录句柄保持稳定，需要证明 Windows 分享模式、重命名兼容性、文件占用、路径替换和崩溃后恢复均成立。不能以 POSIX open/rename 行为推断 Windows。固定句柄也不自动证明整棵树成员集合不变。

## 15. 代码组织、兼容性与实施纪律

### 15.1 用最小抽象表达真实边界

- glob 编译是纯函数缓存，不需要一个配置服务。
- SVN 固定属性与 raw 缓存是任务资源，不需要跨应用全局缓存。
- raw → export 是转换边界，可以抽小函数；不要把六种 VCS 全部改成新框架。
- HTML store 是报告生命周期资源，不能替代 exporter 或恢复所有权。
- 批量 Git 探针是进程协议，必须与 raw batch 的用途和验证分开。

共享代码可以减少重复，但只有当输入身份、错误语义和生命周期一致时才合并。函数名相似不是合并依据。

### 15.2 兼容检查点

1. 新参数尽量可选且带兼容默认值，避免破坏现有测试与直接 API 使用。
2. 内部快速路径只能在明确满足前提时使用；前提不成立走现有完整路径，不返回“未处理成功”。
3. 不能识别测试桩并给它特殊业务行为；测试应验证合同，而不是迫使生产代码特殊判断 mock。
4. 现有需要注意的用法：直接赋值 exclude_patterns、绕过 `__init__` 的桩、读取 FileDiff 正文、显式启用限制、原始 bytes writer 回退、特殊路径的一次性 Git 读取。
5. 既有支持范围不能悄悄缩小；新接口支持范围扩大时也要说明，不把拒绝改为成功而未核对交付字节。
6. Unicode 路径、大小写敏感 Windows 目录、合法 `~` 名称以及真实短别名必须继续区分。

### 15.3 批次收尾

每批先完成针对性验证，再进入下一批。不要每改一行就跑完整回归，也不要直到所有模块都改完才第一次跑测试。

将代码差异保持可拆分：A 类基础优化、B1 渲染、B2 端点、B3/B4 归档、B5 Git、C 报告分别能解释。未得到提交指令时不为“分批”擅自 commit，可以通过差异说明和测试记录保持可审查性。

如果用户后来要求提交，采用范围清晰的中文提交；是否推送按当时明确指令，不从本方案推断。

## 17. 性能基准设计与验收口径

### 17.1 通用运行规则

- 固定随机种子，输入内容可重建；两个版本的输入逐文件摘要一致。
- 基线与候选放独立源码目录，在不同进程执行，避免 Python 模块缓存串用。
- 至少三次；推荐交替 baseline/candidate，而不是先连续跑完所有 baseline 再跑 candidate。
- 不与完整回归、打包、扫描其他大目录同时运行。
- 说明是否包含冷启动、夹具创建、缓存预热、报告、提交和清理。
- 墙钟测量与 tracemalloc/详细 profile 分开，避免测量工具成为主要耗时。
- 每次性能运行都验证业务输出，不能只测“函数返回了”。
- 不要求跨机器固定秒数，优先使用进程/请求/读取量等结构指标，再报告同环境时间。
- 有波动时保留每次原始值；不只挑最好一次，不删除慢样本来美化结果。

### 17.2 基准案例定义

#### P01：长行字符匹配

```text
old = 'ab' × (N / 2) + 'X'
new = 'ab' × (N / 2) + 'Y'
N = 2,000 / 4,000 / 8,000
```

分别计 `_changed_pair`，以及完整 DiffEngine 中单条、少量不足 64 行、64 行及以上替换案例。64 行案例除第一行外再放 63 行 old-row/new-row。逐例记录实际渲染器、选择原因和调用次数，不能仅由输入行数推断路径。核对两侧每个字符、精确变化行数和高亮范围；各路径的改进或未改善分别报告。

#### P02：变化区间中间的重复行

```text
old = ['old-start'] × 64 + ['repeat'] × N + ['old-end'] × 64
new = ['new-start'] × 64 + ['repeat'] × N + ['new-end'] × 64
N = 2,000 / 4,000 / 8,000
```

同时测行匹配和最终报告，全文验证所有行，上下文验证原始行号。补充长公共块前只插入/删除一行、重复块移位、两侧重复数量不同，避免仅为这个模板写特殊分支。已知公共块应保持对齐；记录相同/高亮区域并保留代表性前后报告，不接受统计只改一点、展示却把整个公共块标成变化的退化。

#### P03：glob

使用当前默认规则，不复制一个会过期的常量表。生成 20,000 条未排除源码路径、1,000 条 target/classes 路径及代表性边界路径。分别统计规则转换次数与总耗时，结果逐项相同。

#### P04：Git 小文件进程开销

真实本地 Git 仓库，12/100/500 个小文本文件，两次提交，每个文件改一行。分别测试 LF/autocrlf=false、有效 CRLF 转换以及几种实际属性组合。

分开记录仓库固定开销、raw batch 进程数、blob 逻辑请求数、微小 filters 逻辑请求数、filters 进程数、mode 查询进程数、传输/输出字节数。核对导出与预期检出字节。

较大档可以在小档正确后运行。批处理若减少进程却显著增加扫描整仓库开销，需如实报告。

#### P05：SVN 获取复用

真实本地 SVN 仓库，6/100 个修改文件，普通与多版本分别测；补充有 EOL、rename、项目根移动和二进制案例。

分别记录 cat、proplist、info/log 等调用，唯一固定端点数量、网络/子进程内容字节、raw/cache/derived export 磁盘字节、NUL 扫描字节，以及缓存身份核验是否融合到已有读写流。核对没有用额外预扫描抵消获取复用收益。网络延迟模拟只能标为模拟，不能宣称内网已验证。

#### P06：TAR 顺序提取

两端各 3 个 1 MiB 随机成员，分别 tar/gzip/bzip2。随机数据避免因极端压缩比触发真实安全限制；另有单独的高压缩比拒绝测试。

计量有效 payload、解压后的读出字节、写盘字节、预检描述驻留、峰值内存与时间。再用较多小文件案例检查目录与元数据开销。递归案例记录声明预留和实际消费各自的次数/字节，防止改入口后漏算或重复计量。私有 gzip 方法计数可用于探针，但最终基准说明其 Python 版本依赖。

#### P07：排除成员正文不写盘，名称占位保留

构造 ZIP/TAR 两端各若干 `.class`、日志、保留配置和嵌套包。分别记录总成员、展示成员、声明/实际展开字节、保留正文写盘字节、排除正文写盘字节、文件/目录占位数量、实际采用的空间估算。第一阶段优化样本的排除正文写盘为 0，排除名称创建次数不要求为 0；被排除成员仍执行必要损坏检查。全量公共兼容路径单列，不合入优化命中统计。

在单根选项开/关及递归中重复一组代表性案例。覆盖保留名称碰撞、长名称与实际短别名冲突、合法 `~` 名称、权限变化与目录替换；检查占位保持完整顶层结构，且最终过滤后不泄漏到报告或交付。开启该优化后的主交付与原方案相同，不能只比较报告数量。

#### P08：生成端内存

分别使用很多中等文本、单个大文本、含多层归档的成员树，并保留一个普通小报告对照。先测现有结果对象的驻留，再测差异生成增量和模板输出增量；同时记录片段数、临时文件数、打开次数和读写量，所有测试完成后核对完整报告。

阶段 C1a 的验收是多文件累计 HTML 驻留降低；C1b 才涉及单个大文件峰值。不能把两个目标混在一个“内存下降”数字里。

#### P09：浏览器

用同样的完整报告内容比较：加载、DOM 节点数、首个文件/包内成员展开、过滤、连续切换、峰值或稳定内存。使用实际浏览器运行方法记录版本和参数；无头与人工观察分开描述。

不得以“HTML 文件较小”推断浏览器内存下降；本轮不要求压缩/删减报告正文换取体积。

#### P10：完整任务

已有 `tools/benchmark_archive_all_vcs.py` 可作为全工作线程测量入口；核对实际计时包含导出、递归分析、报告/说明、提交和清理。普通/递归交替至少三次，所有产物核对。

`tools/benchmark_performance.py` 的既有 Git 项不包含最终事务，`tools/benchmark_folder_scan.py` 不代表整个 GUI。使用时继续保留这些标签。

#### P11：事务元数据复用
