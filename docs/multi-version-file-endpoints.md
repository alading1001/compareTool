# Git/SVN 多版本文件端点设计

- 状态：已实现并通过测试
- 首次确认及实现日期：2026-08-24；最近完整性与兼容性收口：2026-08-31
- 适用模式：Git多版本、SVN多版本

## 实现状态与边界

`vcs/multi_version_vcs.py` 已使用文件身份追踪和文件级端点快照替代遗留的统一基线重放算法。它不再执行 Git cherry-pick 或 SVN merge，也不会修改真实项目目录。

界面名称已经统一为“Git多版本 / SVN多版本”；内部配置值仍保留 `git_multi` / `svn_multi`，旧多项目任务中假的“基线 + 选中版本”会在加载时迁移为“文件级首尾端点”。

## 唯一目标语义

选中版本只负责两件事：

1. 决定哪些逻辑文件进入候选集合；
2. 为每个文件分别确定首次和末次选中变更。

对每个逻辑文件 `f`：

```text
S_f = 所有选中版本中，真正修改过 f 的版本集合
first_f = S_f 中历史最早的版本
last_f  = S_f 中历史最晚的版本

old_f = f 在 first_f 发生之前的真实状态
new_f = f 在 last_f 提交之后的真实状态
报告  = old_f 与 new_f 的最终净差异
```

- Git 只支持当前分支第一父历史；`old_f` 来自 `first_f` 的第一父提交，`new_f` 来自 `last_f`。
- SVN 按 revision 排序；`old_f` 来自 `first_f - 1`，`new_f` 来自 `last_f`。
- 不使用当前工作副本或 HEAD 代替 `new_f`，因为它们可能已包含更晚版本。
- 不使用全局最高选中版本强制读取所有文件；不同文件允许来自不同版本。
- 不重放提交、不三方合并，也不制造历史中不存在的合成文件。

## 已确认场景

```text
r3 修改 B.java（选中）
r6 修改 A.java（选中）
```

结果允许为：

```text
B.java：old = B@r2，new = B@r3
A.java：old = A 自己首次选中变更前的状态，new = A@r6
```

若同一文件在 r3、r6 均被选中版本修改，而中间 r4 未选中：

```text
old = 文件@r2
new = 文件@r6
```

r4 不单独展示，但它对该文件最终状态造成的净影响会自然出现在首尾差异中。选择 r6 表示认可 r6 提交时该文件的完整真实状态；若 r4 内容不应上线，应在 r6 中先回滚或修正。

若 r4 未选中，r6 是选中版本中第一次修改该文件的版本：

```text
old = 文件@r5
new = 文件@r6
```

只展示 r6 相对其前一版的净变化。

## 净结果规则

中间修改、删除、恢复和重新新增只用于确定路径对应关系，不展示历史过程：

- 左侧不存在、右侧存在：新增；
- 左侧存在、右侧不存在：删除；
- 路径相同、内容不同：修改；
- 起始路径与最终路径不同：重命名，内容仍按首尾状态比较；
- 路径和内容最终均相同：净零变化，不进入报告和导出。

改名可能发生在未选中的中间版本。只要后续选中版本继续修改改名后的路径，就以首次选中变更前的旧路径作为左侧，以末次选中变更后的最终路径作为右侧。报告只显示首尾改名，不展开中间路径历史。

## 报告与导出合同

报告和导出必须使用同一组文件端点，不允许报告一套、oldVersion/newVersion 另一套。

```text
oldVersion/<old_path> = old_f 的完整文件内容
newVersion/<new_path> = new_f 的完整文件内容
```

- `newVersion` 中是可直接阅读或覆盖对应路径的完整源码/二进制文件，不是补丁片段。
- `newVersion` 是不同文件各自末次选中版本状态的集合，可能混合多个 revision/commit；它不是某一个版本的完整项目源码快照。
- 删除文件只进入 `oldVersion` 和删除清单；新增文件只进入 `newVersion`；重命名使用旧路径导出 old、最终路径导出 new。
- 编码、BOM、换行符和二进制字节继续遵守现有导出合同。

每次生成还必须在报告、`oldVersion` 和 `newVersion` 同级生成带 UTF-8 BOM 的上线操作说明：单项目使用 `<项目名>_上线操作说明.txt`，多项目使用 `上线操作说明.txt`，避免同一批次内多个单项目相互覆盖：

- 列出需要删除的旧路径；重命名的旧路径也进入删除清单；
- 单独列出 `旧路径 -> 新路径` 的重命名关系；
- 多项目路径始终带项目名，不受报告展示选项影响；
- 即使没有删除或重命名也必须生成，并明确写“无”；
- 报告详情和弹窗路径清单默认完整生成，不因预计文件数、路径字节或 HTML 体积降级/截断；最终报告流式写入临时文件并原子替换，默认不设体积上限；
- 报告、说明文件和两套导出目录必须在批次级进程锁内作为同一事务提交或回滚；耗时生成前从用户配置的可信输出根向下校验并捕获所有正式目标状态，源码/报告/说明 stage 直接创建在可信根并在写入前复核，锁内再次检查后才能提交，避免慢任务覆盖较新结果或生成期间的 batch junction 把暂存内容引到根外。固定锁文件拒绝链接、联接点和硬链接。恢复 journal/decision 必须通过独立的每用户 HMAC 私钥验签，并绑定 stage/target/backup 的文件系统身份与流式内容摘要；可信输出根可以是私钥路径的广义祖先，但正式输出目标不能指向或覆盖私钥。删除前先移动到由签名 token/源路径确定性派生的隔离名，恢复机显式收敛隔离待删和旧目标已恢复等中间态，目标树、备份或任一祖先发生替换时保留现场。签名 journal 独立授权有日志恢复；PID stage marker 只授权无日志孤儿 stage 清理。旧版 v1 无签名 journal 不能授权任何恢复或删除，严格识别后只告警并原样保留，但不得永久阻断本次新结果提交。每次多项目生成使用独立 `multi_run_时间戳_随机标识` 目录，消除同毫秒并发碰撞；启动恢复只多扫描严格命名的这一层目录，禁止递归普通输出目录或让历史报告共享会被后续运行覆盖的说明文件和 old/new 根。

## 实现要点

当前实现继续复用：

- DiffEngine 的文本、格式和二进制差异；
- FileExporter 的完整字节导出和事务提交；
- 临时 old/new 快照目录；
- 排除规则、多项目总报告和版本列表多选交互。

端点规划保留每个文件自己的 `old_version`、`new_version`、`old_path` 和 `new_path`。重命名并修改内容不会退化为两个互不相关的删除/新增记录。

- Git：只分析当前分支第一父历史，合并提交相对第一父提交计算；父对象在浅克隆边界缺失时中止。先以正常重命名阈值追踪身份，并用紧凑路径组保存同提交 `D/R → A/R/M` 竞争结构；所有文件级端点确定后，只有不同逻辑实体真正跨越选中端点时才运行低阈值第二遍 diff 或逐对评分，首个命中即停止。跨提交只保存待定删除活动区间和后续 `A/R/M` 目标事件，按 `start < target_step <= end` 与最终选中步过滤后才评分，不在历史遍历阶段展开乘积。需要评分时把 source/target blob 流式写入隔离临时目录，用 `git diff --no-index --find-renames=50%` 重算 Git 原生分数；历史规模、候选矩阵、评分次数和评分字节默认不设性能型硬上限。候选身份跨越选中端点且不能唯一确认时整体失败，不生成猜测结果。
- SVN：解析当前项目 URL 的 `svn log --xml -v` 历史，用 `copyfrom-path`、revision 对应的项目仓库前缀和删除覆盖关系追踪身份。项目根、祖先或嵌套目录移动，同 revision 子文件改名、移出目录、覆盖已有目标，延迟 copyfrom 和移动后删除源祖先都要保持同一逻辑文件；普通 copy 的源仍存在时保持两个独立文件，同源多目标且自然后缀消失时降级为删除源和新增各目标。
- 两种模式：排除规则在每一个历史步先于身份竞争和端点读取生效，跨排除边界的 rename 降级为 A/D；目录剪枝只能由同一条规则完整覆盖不同深度后代。导出字节与仓库原始字节分别流式快照到磁盘，前者供 oldVersion/newVersion，后者用于识别 BOM、编码和换行符净差异，净零判断使用分块文件比较，不同时保留四份内容。默认不为了预计写盘量额外查询所有端点大小，也不设端点文件数、源字节或预计写盘量的性能型固定上限；实际端点读取或写盘失败才中止。SVN log/list 使用增量 XML 解析且默认不限制生成命令输出体积；目录覆盖、移动和排除前缀使用前缀索引或路径层级查询，不能形成文件数×目录数的重复扫描。Git 的 commit、检出配置和有效属性固定后再读取；SVN 的 URL、仓库根、UUID 与 peg revision 由同一次 XML info 固定，历史上界不得再使用可变 HEAD。Git 历史中的类型变化只延续同路径身份，不因无关中间文件全局失败；最终选中端点出现非普通 mode、`svn:special` 或其它非普通文件时，必须在净零过滤前中止。成功或失败后都清理临时目录。
- 交付事务：正式单项目源码 stage 位于批次根的内部随机 wrapper，不写入 `oldVersion/newVersion`；只有名称和所有权标记同时匹配的无日志强退遗留才允许清理，同时不扫描用户源码树。多项目在外层 stage 内逐项目生成，最终整体替换 old/new 根，避免上次项目残留。报告、说明和两侧源码始终同组提交或回滚；同一批次的并发实例必须由进程锁互斥。

## 验收底线

自动化验收覆盖：

1. 不同文件使用不同首尾版本；
2. 同一文件跨选中和未选中中间版本；
3. 未选中改动发生在该文件首次选中变更之前；
4. 中间改名以及改名同时修改内容；
5. 新增、删除、删除后重建；
6. 多次选中变更最终完全抵消时不输出；
7. Git 当前分支第一父约束；
8. SVN 文件和目录移动；
9. 空文件、二进制、编码、BOM 和换行符；
10. 报告左右内容与 oldVersion/newVersion 导出字节完全一致；
11. Git 浅克隆、跨越选中端点的低相似重命名、重复/高相似竞争来源、跨提交移动和同路径重建噪声均 fail closed；无关中间低相似重命名和类型变化不阻断；
12. SVN 项目根/祖先/嵌套目录移动、同修订子文件改名、移出目录、覆盖已有目标、延迟 copyfrom、源祖先删除、普通 copy、同源多目标，以及目录移动同 revision 的普通子文件 copy；
13. 多项目任务旧配置迁移，不能继续保存假的“基线 + 选中版本”；
14. 单/多项目四类产物事务回滚、强退孤儿暂存清理和多项目旧目录移除；
15. 多版本界面与单项目报告使用“选中版本 / 生成结果”，不得伪装成统一“旧版本 / 新版本”。

主要回归用例位于 `tests/test_multi_version_file_endpoints.py`、`tests/test_review_regressions.py`、`tests/test_adversarial_regressions.py`、`tests/test_terminal_round_adversarial_regressions.py`，以及五个 `tests/test_*_compatibility_after_aug27.py` 兼容性套件。
