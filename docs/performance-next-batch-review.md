## 1. [P2] 重复行锚点破坏长公共块的对齐

位置：`stable_diff.py::_run_anchor`，约第 55–79 行；`_line_opcodes` 约第 101–105 行接受锚点并切分区间。

当前锚点只在连续重复行中挑候选。一旦找到至少 32 行的重复游程，就用它切断两侧区间，没有考虑跨越该锚点位置的更长、非重复公共块。相同内容的游程可作为候选，但不能仅凭它自身真实相等，就推导出将它固定为分割边界能保持整体对齐质量。

实际复现输入（两侧各 2,160 行）：

```python
common = [f'unchanged_unique_{i:04d}' for i in range(2000)]
old = ['old-start'] * 64 + common + ['repeat'] * 32 + ['old-end'] * 64
new = ['new-start'] * 64 + ['repeat'] * 32 + common + ['new-end'] * 64
```

首尾替换使真实 DiffEngine 进入 stable 渲染；中间只是 32 行重复内容移到同一个 2,000 行公共块之前。

| 指标 | HEAD 原 stable 渲染 | 当前 stable 渲染 |
| --- | ---: | ---: |
| 保留为相同的公共块行数 | 2,000 | 0 |
| 全文中显示为相同的行数 | 2,000 | 32 |
| HTML 高亮 span 数（仅辅助计量） | 448 | 4,512 |
| 独立精确统计：新增/删除 | 160 / 160 | 160 / 160 |
| 左右全文还原 | 正确 | 正确 |

同一问题也已在工作线程采用的 `detail_store` / `iter_stable_diff_table` 路径复现，不能只修公共字符串入口。它影响报告可读性，未观察到本例丢失正文或交付字节错误。

这正是方案第 8 节要求避免的“统计只改少量，页面却大面积额外标色”。现有测试主要覆盖纯重复块及重复块拆分/合并，没有覆盖重复游程与更长的非重复公共块竞争，因此全文还原与统计测试全部通过仍会漏掉它。

建议修复方向：

- 将可确认的非重复公共块/单调锚点纳入选择，在其余区间内使用重复游程优化；或为重复游程分割增加足以防止上述退化的适用条件。
- 不要求所有重复输入的唯一最优对齐，但不能无条件优先固定一个较小游程，导致本来稳定的长公共块失去对齐。
- 不用提高 32/128 阈值掩盖一个样本，不用大面积机械按行号配对换速度；也不要全量退回原算法而丢失已确认的重复行性能收益。

修复验收：

1. 上述样本、交换新旧两侧、改变重复块长度和公共块长度，稳定公共块保留合理对齐。
2. 覆盖全文/上下文、字符串/stored 两种入口；全文仍能还原，上下文不隐藏真正变化，统计不变。
3. 将本例转成正式回归，验收公共块的 equal 区间或等价展示性质，不断言随机 DOM ID。
4. 原 E01/E02 的 2k/4k/8k 性能样本仍测三次，避免修质量时恢复已消除的平方级工作。

证据：`probe_alignment.py`、`alignment-result.json`、`baseline_alignment.html`、`candidate_alignment.html`、`candidate_stored_alignment.html`。脚本用 HEAD 的原 stable 渲染器与当前真实引擎入口对照，基线提取文件保存在本次证据目录，未改工作区源码。

## 2. [P2] Git 批量探针按端点保留过多存活进程

位置：`vcs/git_checkout.py::_probe`，约第 178–187 行；`cleanup` 约第 222 行。

当前 `_probe_batches` 以 `(endpoint, tuple(args))` 为键创建并保留子进程，正常成功后直到整个 snapshot cleanup 才关闭。固定端点/策略隔离是必要的，但不等于每个端点的进程都需要同时存活到任务结束。

普通 Git 的两个端点样本显示进程启动次数减少；多版本每个文件来自不同提交时，固定端点会很多，此时资源生命周期的问题才显现。

本次创建独占本地 Git 仓库：初始提交包含 24 个文件，随后 24 次提交分别修改一个文件，再选中全部 24 次提交。实际调用 `GitMultiVersionVCS` 并校验准备好的端点字节。

| 指标 | 实测 |
| --- | ---: |
| 选中提交 / 变更文件 | 24 / 24 |
| 启动的 filters 探针进程 | 25 |
| 同时存活的 filters 进程峰值 | 25 |
| 端点准备完成后仍存活 | 25 |
| cleanup 后仍存活 | 0 |

本例成功生成端点，没有复现资源耗尽，也不是退出后进程泄漏。问题是**正常任务中的峰值资源开销随不同端点数增长**：子进程、管道和诊断临时文件同时保留；更大的多版本输入会继续增加这些资源。这与降低开销的目标不符，现有“12 文件、两个端点”的测试不足以覆盖。

建议修复方向：

- 优先按固定 endpoint/策略分组完成微小探针，缓存判定好的 mode，再关闭该组通道；后续导出读取 mode 结果。
- 若调用结构更适合少量可回收通道，也可以限制同时保留的空闲通道数量并安全重建。该限制是内部资源复用策略，不能限制用户可选提交数、文件数或结果完整性。
- 保持 `GIT_ATTR_SOURCE`、filter 拒绝策略、路径协议和失败关闭规则。不能为共享一个长期进程而混用不同端点环境。

修复验收：

1. 上述 24 提交案例以及更大独占案例，峰值存活通道不再跟不同端点数一起无界增长。
2. 同端点多文件仍复用进程；统计启动次数、逻辑请求数和峰值存活数，不能只统计累计启动次数。
3. 端点导出、属性/换行转换及协议失败矩阵保持；成功和异常退出均关闭本任务进程。

证据：`probe_processes.py`、`process-result.json`。仓库是本次审查创建的合成输入，所有探针进程已经随本次 VCS cleanup 退出；没有操作用户业务仓库。
