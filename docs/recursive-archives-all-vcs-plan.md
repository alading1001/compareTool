# 递归压缩包报告扩展到全部六种模式：审查与实施方案

日期：2026-09-26

状态：已实施，作为设计依据和验收场景索引保留。以下正文记录实施前的分析；当前规则见 [包内报告规则](nested-archive-report.md)，六模式实现及验收见 [验证记录](recursive-archives-all-vcs-verification.md)。源码实现已提交为 `fe757c9`；该提交不代表 EXE 已重新打包。

核查基线：`8b7be5f66d9c7caa64cbe923f7aa69b8c3e6c3db`（修复重复行渲染性能与递归报告内存占用）。

本次读取了用户提供的《CompareTool_myself项目网页6Pro执行》对话，包括“全部模式是否可行”的分析，并对照当前工作区源码、合同和测试进行了静态核查。开始核查时 Git 工作区干净。本次只编写本方案，没有修改程序、运行完整回归或重新打包；对话中的历史测试数量与性能数字不作为本轮独立验证结果。

## 1. 结论与对 6 Pro 分析的评价

**可以扩展到 Git、SVN、文件夹、压缩包、Git多版本和 SVN多版本，并覆盖六种模式混合的多项目总报告。6 Pro 的总体判断正确，主要风险也识别到了，但其回复仍是可行性分析，还缺少几个决定实现正确性的具体选择。**

它说对的部分：

- 递归逻辑已经独立在 `archive_report.py`，不需要重写六套解压、比较和模板。
- 多版本必须继承外层包自己的文件级首尾端点，不能使用当前工作副本、统一最高版本或重放选中提交。
- 包内差异只能附加到报告，不得改变主交付清单、原包字节或宿主删除指令。
- 历史对象读取失败与该侧确实不存在必须区分；错误要使整次生成失败。
- Git 属性、SVN 属性、LFS、重复读取、共享预算、混合任务配置都需要考虑。
- 必须保留 `8b7be5f` 的重复边界匹配优化和递归 `include` 流式渲染。

需要补足或收紧的部分：

| 问题 | 当前核查结果 | 实施要求 |
|---|---|---|
| “两处限制”过于概括 | 实际有 5 个 GUI/配置/任务执行限制和 2 个递归模块类型限制，旧测试也明确断言 Git/SVN 不可启用 | 逐项修改，不能只解锁复选框 |
| 分析原始字节还是交付字节未定 | Git/SVN 的 raw 接口与 export 接口含义不同，多版本也有两套快照 | 包内分析以本次最终导出字节为准；raw 继续服务现有差异分类 |
| “尽量复用同一份内容”缺少落点 | `FileExporter.prepare_export()` 已能生成完整但尚未提交的 old/new 暂存树 | 优先直接分析待交付暂存文件，无需给四种 VCS 新建缓存系统 |
| 没明确版本标签与端点侧别的区别 | `DiffResult.old_version/new_version` 保留输入文字；普通 `FolderVCS` 对不识别的版本会走新侧 | 新接口显式传 `old`/`new` 侧别，禁止把提交号或“文件级首尾端点”直接传给临时 FolderVCS |
| 对所有“转换”的表述不够精确 | 有属性不等于发生转换，raw 不同于 export 也不自动构成错误 | 沿用现有转换合同；分析有效交付包，不能绕过属性，也不能新增一刀切拒绝 |
| 没给出事务和生命周期改法 | 当前单项目先递归、写报告，再准备导出；多项目在准备任务时递归，之后才导出 | 调整顺序但继续一次成组提交；解析器只借用 stage，不负责删除 stage |
| “同一端点只取一次”需要限定 | 普通 SVN 精确重命名已可能额外 `svn cat`；多版本已分别生成 raw/export 快照 | 要求新增递归阶段不增加仓库内容读取，不承诺整条历史流程总共一次 |
| 验收还不够具体 | 仅有“历史版本、改名、失败”不足以防止子项目串入、配置丢失或两侧读成同一份 | 使用第 9 节的验收矩阵，覆盖实际工作线程、真实本地仓库和故障注入 |

**推荐方案：保留现有 VCS 规划和导出；先把主交付文件写到本次私有暂存目录，再用这些文件做包内分析，最后一次提交报告、说明及 old/new。**

这是基于现有代码结构提出的实施建议，尚未经过本轮运行验证。它比“为每个 VCS 增加一套包缓存”少一层版本与转换一致性管理，但会改变生成顺序，因此必须验证异常清理、暂存内容绑定和事务恢复。

## 2. 目标与本轮边界

### 2.1 用户可见目标

六种模式都可以勾选现有“递归查看压缩包内部差异（仅报告，交付保留原包）”。默认仍关闭，每个来源保存自己的设置，每个多项目任务保存选项快照。

报告只展开主变更清单中受支持的包，再逐层处理变化的子包。普通文件导航、主文件树和纯文本变更清单维持原有语义。

| 模式 | 包的历史/来源语义 | 最终交付 |
|---|---|---|
| Git | 固定的两个提交，在所选项目范围内对应的包 | 现有 Git 导出规则所得的完整包 |
| SVN | 固定仓库身份、URL/peg 和两个数字 revision 对应的包 | 现有 SVN 导出规则所得的完整包 |
| Git多版本 | 每个包自己的首次选中变更前、末次选中变更后端点 | 该包两侧完整导出端点 |
| SVN多版本 | 同上，继续使用现有历史身份规划 | 该包两侧完整导出端点 |
| 文件夹 | 当前比较已固定的新旧文件快照 | 完整原包 |
| 压缩包 | 最外层归档比较所得的变更成员 | 现有外层成员；其中若有 WAR/JAR，仍交付完整 WAR/JAR |

“完整原包”在 Git/SVN 场景中指**按现有导出合同得到的完整包文件**，不承诺无视属性后永远与仓库 raw blob 相同。包内功能不重新压缩、不修补、不重新签名。

### 2.2 本轮不扩展的能力

- 不自动编译源码生成包；只处理所选端点中存在的文件。
- 不自动拉取 LFS 对象、不执行 smudge/process 或包内程序。
- 不增加 RAR/7z、加密包、CLASS 反编译、跨包成员移动推断。
- 不更改 Git/SVN 历史身份算法、净零过滤、主重命名算法或默认排除模板。
- 不把包内分析结果当成签名校验、软件成分扫描或上线业务验收。
- 本方案本身不授权改写用户业务仓库、用户配置、历史交付或正式 EXE；正式打包、提交和推送按届时用户指令执行。

## 4. 推荐实现：分析待交付的暂存文件

### 4.1 数据流

```text
现有 VCS 固定版本、项目范围、属性与身份
                 ↓
现有 DiffEngine 形成主 DiffResult
                 ↓
现有 FileExporter 写好本次 old/new 暂存交付树
                 ↓
显式 old/new 端点来源只读借用这些文件
                 ↓
现有安全解压器 + 包内 DiffEngine + 整报告共享预算
                 ↓
仅填充 FileDiff.archive_details
                 ↓
流式生成报告、生成现有上线说明
                 ↓
复核暂存内容和正式目标 → 原事务成组提交
```

六种模式在 FileExporter 之前保留原有区别，递归模块只关心实际文件及其旧/新侧。多版本包的专属端点已体现在导出文件中，不再解读选中版本字符串。

### 4.2 端点来源接口

可在 `archive_report.py` 内新增小型 `StagedArchiveEndpoints`，或放在一个专用模块中。避免新增覆盖整个 VCS 层的大型框架。

建议能力如下，名称可调整，语义必须保留：

```python
class StagedArchiveEndpoints:
    # old_root/new_root 是本次已完成导出的项目级 stage 根。
    # trusted_root 是用户配置的可信输出根，不能从可替换的子目录重新猜。
    def path_for(self, side, relative_path):
        # side 严格为 'old' 或 'new'；其它值必须报错。
        # 校验根、路径组件、根内边界和预期存在的普通文件。
        # 返回只读使用的实际路径，不创建、不删除任何交付文件。
        ...
```

入口可设计为：

```python
enrich_archive_reports(
    result,
    vcs=None,               # 兼容现有 folder/archive 调用
    *,
    endpoints=None,         # 新 GUI 生成链路显式传入暂存端点
    show_full_context=True,
    exclude_patterns=(),
    budget=None,
)
```

约束：

1. 顶层 GUI 调用使用 `endpoints`；已经提供端点时不得再从 VCS 获取包内容。
2. 原有 folder/archive 单元调用可保留兼容适配，避免无必要改写全部测试和递归内部实现。
3. 递归到包内下一层时，仍使用 `_ReportArchiveVCS` 已固定的解压结果，不能回到顶层 stage 找同名成员。
4. 不通过修改 `result.old_version/new_version` 来“临时切换”到 old/new。
5. 不调用新的 FolderVCS `get_changed_files()` 重新识别主列表，否则可能丢失历史重命名、元数据或多版本身份。
6. 不为这个只读适配器添加删除 stage 的析构器、cleanup 或所有权标记。stage 仍归 FileExporter 管理。
7. 不从正式 `oldVersion/newVersion` 读取，也不读取工作副本；这些都可能属于别的时间点。

### 4.3 A/D/M/R 的路径选择

| 主变更类型 | 旧侧 | 新侧 |
|---|---|---|
| 新增 A | 明确不存在，不调用旧侧读取 | `file_path` |
| 删除 D | `file_path` | 明确不存在，不调用新侧读取 |
| 修改 M、格式 F、属性变化 | `file_path` | `file_path` |
| 重命名 R | `old_path`，缺省才使用 `file_path` | `file_path` |

F 是报告分类，具体枚举与写入分支继续遵从现有实现，不额外发明变更类型。

只有 A/D 或已经被上游规范化为 A/D 的跨边界事件能产生空侧。修改包丢了一侧、拒绝访问、对象缺失、读取中断都必须报错，禁止捕获后返回 `None` 或空文件。合法空 ZIP/TAR 与零字节损坏文件不是同一回事。

### 4.4 单项目流程

在 `_do_generate()` 中：

1. 保留源/输出分离、仓库元数据边界检查和生成前正式目标状态捕获的位置。
2. 保留现有 VCS 创建、版本检查、排除设置和主 DiffEngine。
3. 开启递归时，先调用 `FileExporter.prepare_export()`，立即保存返回的 pairs；它尚未修改正式输出。
4. 从 pairs 对应的实际 old/new stage 构造端点来源，校验两个目标与预期 old/new 一致，不能按 wrapper 名称推测路径。
5. 按第 5 节固定此次待分析的暂存内容，调用递归分析。
6. 用同一个主结果生成报告与上线说明。
7. 把同一组源码 pairs、报告 stage、说明 stage 交给现有成组提交。
8. 在同一个 `try/finally` 生命周期内管理所有 stage。递归失败、报告生成失败和提交失败都必须走原有安全清理。

递归关闭时优先保留原路径；若为了避免重复代码统一前移导出，必须证明关闭时的结果与失败恢复不变。不要维护两套事务实现。

### 4.5 多项目流程

在 `_do_generate_multi()` 中：

1. `_prepare_task_result()` 继续创建 VCS 和主结果，但不再提前递归。
2. 所有任务准备成功后，继续执行主展示路径冲突检测。
3. 按现有方式在可信输出根创建外层 old/new stage，并逐项目调用 `export(..., targets_are_staging_roots=True)`。
4. 等全部项目导出结束，固定两个外层 stage 的内容状态；不要在后续还会写入项目文件时提前固定整树基线。
5. 第二个循环逐项目分析。端点根为安全定位到的 `stage_old_root/项目名`、`stage_new_root/项目名`；选项读取自 `item['task']`。
6. 整次运行仅创建一个 `ArchiveReportBudget`，传给全部启用递归的项目及所有嵌套层。关闭的任务不消耗预算。
7. 全部分析成功后再渲染总报告、生成说明并成组提交外层目录。

当前内层 `export()` 的替换目标位于外层 stage，属于暂存树组装，不是提交正式交付。不要误改成逐项目写到正式 `multi_run_*` 下，也不要取消 `targets_are_staging_roots=True`。

`project_results` 必须保存每个需要清理的 VCS。任务准备失败时清理正在创建的对象，外层 finally 清理之前已完成准备的对象；不要把对象所有权转交给报告子树。

## 5. 从分析到提交的内容一致性与所有权

### 5.1 为什么还需要绑定暂存内容

直接复用 stage 解决了“又从仓库读取另一份文件”的问题，但不能把“临时目录”自动等同于不可变内容。

当前 `_replace_outputs_locked()` 在提交阶段才首次为 stage 计算 `stage_identity`，随后在安装前复核。它能保护提交阶段的对象一致性，但**没有直接绑定更早进行包内分析时所读到的内容**。这是采用本方案时要补齐的链路，不是本轮已经动态复现的漏洞结论。

### 5.2 推荐的最小闭环

可以给 `_replace_outputs()` 和 `_replace_outputs_locked()` 增加可选 `expected_stage_states`，默认 `None` 保持原调用兼容：

1. 仅在本次实际需要分析包时，于源码 stage 写完、递归开始前，调用现有 `_tree_identity()` 捕获源码 stage 的内容身份。
2. 单项目记录最终提交的两个项目级 stage；多项目记录最终提交的两个外层 stage。
3. 递归读取继续使用既有安全打开、稳定句柄、FileId/路径身份与解压器复核，不得仅靠根目录快照替代读取保护。
4. 持有提交锁后，在对正式目标作任何备份/替换之前，用本来就要计算的 stage identity 与该预期值比较；失败则不提交。
5. 将这次已验证的同一 identity 写入现有 journal 状态，继续沿用安装前复核，不能再无条件刷新成一个较新的身份。
6. 新报告和说明的 stage 仍按现有方式生成与验证。可选字典明确允许只绑定源码 stage；无预期项的原有产物不错误判缺失。

这不需要改变 journal 的签名格式、恢复决策或既有 `stage_identity` 字段含义。只增加“提交使用的身份必须与分析前一致”这一约束。

该方案会增加开启递归时一次源码 stage 的流式身份扫描；应计入耗时，不把它说成零成本。没有候选包时不为此扫描；不要再叠加若干次相同全树哈希。若改用只绑定分析包、并在已有提交遍历中复核的更轻方案，也必须通过同样的篡改与恢复测试，不能只凭 size/mtime 判同。

### 5.3 路径与清理要求

- 沿用 `safe_join`、`ensure_no_link_components`、安全普通文件打开等已有能力；校验要覆盖可信根到 stage、stage 到成员两段。
- 先校验原始路径组件，再使用 realpath 做根内检查；不能先把 junction 解析掉后当成正常根。
- 不使用包名或成员名拼接 shell 命令，不在输入树里创建缓存，不额外复制整份顶层包。
- 临时包展开仍使用 `vcs.temp_storage`，正常结果与普通失败清理自己的临时物。
- 事务回滚未完成时，继续由现有 `_pending_stage_journals` 等机制保留恢复材料，不得强制清理。
- Windows 的 deny-writes 句柄可能阻止重命名/删除：解析完成后按所有权关闭句柄，再进入提交；不能把句柄一直挂在报告对象上。
- 若采用备选方案给普通 SVN 新增持久缓存，要同时增加明确 cleanup：当前普通 SVN 单任务没有设置 `cleanup_vcs`，多任务返回的 cleanup 标志也是 false。推荐的 stage 方案不需要新增这套 SVN 资源生命周期。

## 6. 字节、版本与递归语义

### 6.1 字节标准

唯一比较标准是：**包内报告分析的顶层包，与本次要安装到对应 oldVersion/newVersion 路径的文件内容相同。**

- 正常导出成功且字节为有效受支持归档：直接分析。
- 导出规则本身拒绝的 filter、working-tree-encoding、ident、SVN keywords/externals 等：沿用现有错误，不为递归放宽。
- 导出后应展开的文件不是有效归档：整次递归失败，提示项目、旧/新侧、外层路径和内部链路；不得改用 raw blob 或当前工作副本“救活”。
- raw 与 export 不同不自动失败，存在 `.gitattributes` 或 `eol` 也不自动失败；是否允许转换由既有导出合同决定。
- 不因为扩展名是 `.jar` 就新增“跳过现有检出转换”的捷径。

Git 官方说明 `text/eol` 能影响检出字节，因此仓库原始对象不能无条件替代交付文件。项目当前支持与拒绝哪些转换，仍以项目合同和实现为准。[Git gitattributes 文档](https://git-scm.com/docs/gitattributes)

### 6.2 LFS 的范围

LFS 指针与实际大文件不是同一内容，官方指针规格包含版本、对象标识和大小等字段。[Git LFS 指针规格](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md)

若现有 Git 属性检查已经拒绝有效检出过滤器，保留该错误即可。若没有过滤器、最终暂存文件确为规范 LFS 指针，可以在需要展开时给出明确诊断；不要仅发现一个相似字符串就把二进制判成指针，不要为了诊断完整读取大包。自动下载和还原 LFS 对象不在本轮范围。

该诊断不应破坏“字节相同不展开”的现有规则：相同文件可以标注未展开，不能声称其归档格式或 LFS 实体已验证。

### 6.3 多版本

例如选中 r3、r6，A.jar 只在 r3 改动，B.jar 只在 r6 改动，C.jar 在两次都改动：

```text
A.jar：r2 → r3
B.jar：r5 → r6
C.jar：r2 → r6
```

即使工作副本已到 r9，包内报告也必须分别继承以上端点。C.jar 中保留的 r4 未选中修改，若存在于 r6 完整包中，正常显示在最终净差异里；不能人为剔除。

主结果已经净零的包不重新加入；外层已经完成的历史 rename 不再按内容重配；包内成员仍在各自包的两侧快照内比较，不运行成员级 Git/SVN 历史算法。

### 6.4 保持现有递归行为

- 包字节相同：跳过展开；仍保留外层 rename/属性变化，不能宣称内部有效性已核验。
- 包字节不同但无可展示成员差异：保留外层变化及现有说明，不把父包降成无变化。
- 单侧新增/删除：与专门创建的空归档比较，不能把真实读取失败替换成空归档。
- 重命名只有一侧后缀受支持，例如 `a.jar → a.bin`：沿用未支持展开提示，不凭另一侧格式猜测；两侧均支持时可继续比较。
- 包内规则在每层根重新匹配；排除只缩小报告检查范围，不改写包内容。
- `ignore_archive_root` 仅属于用户选择的最外层 archive 模式，不能自动应用到 Git 中的 JAR 或内层包。
- 保留同一份报告 8 层、100,000 成员、10 GiB 累计展开预算，计数包含两端；继续保留每包的既有安全限制。
- 压缩包输入模式的最外层解压与新增嵌套阶段沿用当前计数边界，不在本轮悄悄扩大或减小预算适用范围。
- HTML 仍由递归 include 分片输出，浏览器仍按需实例化局部 DOM；不得恢复返回整棵子树字符串的递归宏。

### 9.6 性能、模板与观测

- 测量递归阶段 Git 内容读取和 SVN `cat` 的新增次数：采用 stage 方案时应为 0。历史规划、raw/export 快照和精确重命名阶段的既有读取独立记录。
- 大包端点仍以流或文件复制处理，不能使用 `read_bytes()`、`get_file_content_bytes()` 或 BytesIO 持有整包作为新主路径。
- 保留 `tests/test_rendering_performance_regressions.py` 的完整成员、最大输出块及重复行检查；不得用少生成内容换取“优化”。
- 测试进度仍通过工作线程观测、主线程轮询更新；文件处理不触发逐文件 Tk 回调，不逐成员写日志。
- 耗时日志失败不使比较失败；成功通知仍在后台清理、任务记录完成后发出。
- 用同一合成样本至少三次记录 off/on 阶段耗时、仓库读取次数和必要的内存指标，标清是否包含导出与最终事务提交；不承诺 30 秒或固定倍率。

建议新增测试模块可命名为 `tests/test_archive_report_all_vcs.py`、`tests/test_archive_report_staging.py`；优先复用现有 archive、Git/SVN、多版本、输出恢复夹具。

先确认原项目 Python 环境可执行，再在独立源码副本目录中运行完整测试，例如：

```powershell
D:\AI\project\compareTool_myself\.venv\Scripts\python.exe -m unittest discover -s tests -q
```

启动前设置本次进程的 TEMP/TMP、`COMPARETOOL_TEMP_DIR` 和测试事务私钥路径到独占 `.tmp` 子目录，并防止测试加载用户真实配置。需要 Git/SVN 的用例使用本地临时仓库；缺命令行依赖或 Windows 权限导致 skip 时要明确报告，不能计作新增模式验收通过。测试夹具的 `_tmp_root` 绝不能指向项目工作目录。

## 10. 备选方案及不建议的做法

如果实际改造中发现 stage 顺序调整与现有流程存在具体冲突，可以采用任务内统一端点适配器，但要先给出冲突证据：

- folder/archive 借用已固定快照；多版本借用交付 `_folder`；普通 Git/SVN 用现有 `export_file_to_path()` 流式生成私有包文件。
- FileExporter 后续必须复用或验证同一份文件，明确缓存所有权、键、转换规则及销毁时机。
- 不直接读 `_raw_folder` 当交付包，不把 raw 导出函数作为绕过转换的捷径。
- 不按文件名、版本显示字符串或 blob OID 单独构成跨任务缓存键；仓库/项目范围、固定端点、路径与检出规则都会影响含义。

此方案可行，但通常比复用 stage 多一套缓存和生命周期。两条路线选一条完整实现，不并行建设两套重复机制。

禁止以下捷径：

```text
仅删除 isinstance 限制或解锁复选框
从工作副本读取同名包补历史内容
把所有模式伪装成 FolderVCS 后重新做主差异
把所有包都读自多版本最高选中版本
将读取错误转换成空包
先发布 old/new，再尝试生成包内报告
把包内成员加入主 files 或上线删除说明
另跑 raw 导出绕过现有属性校验
每个项目重置 ArchiveReportBudget
恢复递归 Jinja 宏或整包内存缓存
```
